# RFC-0000.5: AgentRQ Integration Boundary

**Status:** Proposed  
**Author:** Hamid Hayati Jozani  
**Date:** 2026-07-13  
**Version:** 1.0  

---

## 1. Executive Summary

This RFC defines the integration contract between **AgentRQ** (Agent Control Plane) and **HHJ-CSG** (Execution Governance Runtime). The boundary ensures that:

- HHJ-CSG remains independent from orchestration concerns
- AgentRQ continues managing agent lifecycle and scheduling
- Decision governance operates as an out-of-band evaluation layer
- All execution requests are traceable, auditable, and reproducible

**Key Principle:** HHJ-CSG answers only one question: *"Should this execution proceed under current runtime conditions?"*

## 3. Event Contract

### 3.1 Permission Request Event

**Endpoint:** `POST /v1/gate/evaluate`

**Request Schema:**

```json
{
  "event_id": "evt-uuid-v4",
  "workspace_id": "ws-uuid-v4",
  "agent_id": "agent-uuid-v4",
  "timestamp": "2026-07-13T12:34:56Z",
  "tool_name": "string",
  "tool_params": {
    "type": "object",
    "additionalProperties": true
  },
  "context": {
    "user_role": "admin|user|service",
    "environment": "production|staging|development",
    "session_id": "string",
    "request_id": "string",
    "source_ip": "string"
  },
  "history": [
    {
      "event_id": "string",
      "timestamp": "string",
      "action": "string",
      "result": "success|failure|blocked"
    }
  ],
  "metadata": {
    "priority": "low|medium|high|critical",
    "retry_count": 0,
    "timeout_ms": 5000
  }
}
```

**Field Definitions:**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| event_id | UUID | Yes | Unique identifier for this request |
| workspace_id | UUID | Yes | Workspace context |
| agent_id | UUID | Yes | Requesting agent identifier |
| timestamp | ISO8601 | Yes | Request timestamp (UTC) |
| tool_name | String | Yes | Name of tool/action being requested |
| tool_params | Object | Yes | Parameters for the tool (may contain sensitive data) |
| context | Object | Yes | Runtime context (user, environment, session) |
| history | Array | No | Recent execution history (last 10 events) |
| metadata | Object | No | Request metadata (priority, timeout) |

### 3.2 Decision Response Event

**Response Schema:**

```json
{
  "decision": "allow|deny|ask|defer",
  "confidence": 0.0,
  "risk_score": 0.0,
  "evidence_coverage": 0.0,
  "rationale": "string",
  "lineage_token": "string",
  "timestamp": "2026-07-13T12:34:56Z",
  "processing_time_ms": 0,
  "metadata": {
    "version": "1.0",
    "model": "heuristic|statistical|ml",
    "policy_applied": "string"
  },
  "recovery_recommendation": {
    "action": "string",
    "priority": "low|medium|high"
  }
}
```

**Field Definitions:**

| Field | Type | Description |
|-------|------|-------------|
| decision | Enum | ALLOW: Execute / DENY: Block / ASK: Human review / DEFER: Retry later |
| confidence | Float [0-1] | Confidence in this decision |
| risk_score | Float [0-1] | Assessed risk level |
| evidence_coverage | Float [0-1] | Percentage of context successfully validated |
| rationale | String | Human-readable explanation |
| lineage_token | String | Immutable trace token for replay |
| timestamp | ISO8601 | Decision timestamp |
| processing_time_ms | Integer | Gateway processing latency |
| metadata | Object | Version, model type, policy applied |
| recovery_recommendation | Object | Suggested corrective action |

## 4. Decision Values

### 4.1 ALLOW

**Meaning:** Execution is approved under current conditions.

**Conditions:**
- Evidence coverage ≥ 80%
- Risk score < 0.6
- No policy violations detected
- Confidence ≥ 0.75

**Action:** AgentRQ proceeds with execution.

### 4.2 DENY

**Meaning:** Execution is blocked due to risk or policy violation.

**Conditions:**
- Risk score ≥ 0.8, OR
- Evidence coverage < 50%, OR
- Policy violation detected, OR
- Confidence < 0.3

**Action:** AgentRQ halts execution and logs denial reason.

### 4.3 ASK

**Meaning:** Human review required before execution.

**Conditions:**
- Risk score 0.6–0.79, AND
- Confidence 0.3–0.74, AND
- No clear policy guidance

**Action:** AgentRQ escalates to human operator for approval/rejection.

### 4.4 DEFER

**Meaning:** Gateway is temporarily unavailable; retry with fallback.

**Conditions:**
- Gateway timeout (> 500ms)
- Gateway service error
- Temporary resource exhaustion

**Action:** AgentRQ applies fallback policy (see Section 5).

## 5. Timeout & Fallback Strategy

### 5.1 Timeout Specification

**Default Timeout:** 500ms  
**Maximum Timeout:** 2000ms  
**Configurable:** Yes (per workspace)

```json
{
  "timeout_ms": 500,
  "fallback_policy": "fail-closed|allow-with-mitigation|allowlist"
}
```

### 5.2 Fallback Policies

#### Fail-Closed (Default)

- **Behavior:** If gateway times out or errors, DENY the request
- **Risk:** May block legitimate operations
- **Use Case:** High-security environments, critical systems

#### Allow-with-Mitigation

- **Behavior:** If gateway times out, ALLOW but log for audit
- **Risk:** Execution proceeds without governance check
- **Mitigation:** Mandatory post-execution review
- **Use Case:** Operational efficiency prioritized

#### Allowlist

- **Behavior:** If gateway times out, check against pre-approved allowlist
- **Risk:** Only pre-approved actions execute
- **Use Case:** Hybrid approach (safety + efficiency)

## 6. Security Boundary

### 6.1 Authentication

**Mechanism:** Mutual TLS (mTLS) or Bearer Token

```
Authorization: Bearer <JWT>
```

**JWT Claims:**
```json
{
  "iss": "agentRQ",
  "sub": "workspace-id",
  "aud": "hhj-csg",
  "exp": 1234567890,
  "iat": 1234567800
}
```

### 6.2 Lineage Token

**Purpose:** Immutable proof of decision

**Format:** JWS (JSON Web Signature)

```
lineage_token = base64(header) + "." + base64(payload) + "." + base64(signature)
```

**Payload:**
```json
{
  "event_id": "evt-uuid",
  "decision": "allow",
  "timestamp": "2026-07-13T12:34:56Z",
  "evidence_hash": "sha256(...)",
  "policy_hash": "sha256(...)"
}
```

**Verification:** Any engineer can verify the token using the published public key.

### 6.3 Data Sanitization

**Before transmission to HHJ-CSG:**
- PII redaction (email, phone, SSN patterns)
- Credential masking (API keys, passwords)
- Sensitive payload truncation

**Redaction Rules:**
```
email → [REDACTED_EMAIL]
api_key → [REDACTED_KEY]
password → [REDACTED_PASSWORD]
credit_card → [REDACTED_CC]
```

## 8. Acceptance Criteria

### 8.1 Functional Acceptance

- [ ] Gateway receives permission_request events
- [ ] Decision object is generated for every request
- [ ] Lineage token is created and verifiable
- [ ] Timeout behavior matches fallback policy
- [ ] All decision types (ALLOW/DENY/ASK/DEFER) work correctly
- [ ] Latency p95 < 300ms under normal load

### 8.2 Observability Acceptance

- [ ] All metrics are collected and exportable
- [ ] Logs are structured and queryable
- [ ] Traces can be replayed deterministically
- [ ] Audit trail is immutable and tamper-evident

### 8.3 Security Acceptance

- [ ] mTLS handshake succeeds
- [ ] Lineage tokens are cryptographically valid
- [ ] PII is redacted before transmission
- [ ] No credentials appear in logs

### 8.4 Performance Acceptance

- [ ] p50 latency < 100ms
- [ ] p95 latency < 300ms
- [ ] p99 latency < 500ms
- [ ] Throughput ≥ 1000 req/s
