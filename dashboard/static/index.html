Credential handling

The Gate bearer credential is read from the dashboard process environment and only attached to server-to-server requests. It is never placed in HTML, JavaScript, or API responses.

The Gate separately maintains signing and authority secrets. Those secrets are not supplied to callers or agents.

Execution authority

After an ALLOW path reaches execution reservation, the Gate issues a short-lived signed authority bound to tenant, action, policy and nonce. The protected layer verifies it and consumes the nonce atomically.

Fail-closed

Missing credentials, invalid signatures, expired decisions, tenant/action/policy binding failures and nonce reuse stop the protected execution path.

Important boundary

The console can initiate evaluation, but it cannot bypass Action Gate to execute a tool. That distinction is the whole point, annoyingly enough.

Runtime contract

Agent → Decision → Enforcement → Evidence → Replay

Only the components that are actually present in the repository are represented here. No OAuth provider, HSM/KMS, SIEM or universal identity layer is implied by this console.

01Authenticate

Action Gate validates the server-side bearer credential on protected API routes.

02Bind identity

Tenant, actor, session and action context become part of the decision and evidence record.

03Evaluate

The current policy assigns risk and returns ALLOW, DENY, ASK or SANDBOX.

04Enforce

Execution requires Gate-issued authority with signature, expiry, binding and one-time nonce checks.

05Replay

The stored policy snapshot and action digest are re-evaluated to test decision consistency.
