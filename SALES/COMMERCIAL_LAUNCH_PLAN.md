# Action Gate Commercial Launch Plan

## Objective

Move HamidCognition Action Gate from a technically evidenced release to the first externally verified paid pilot.

The target is not "more GitHub". The target is one buyer, one protected tool, one written scope, one acceptance result and one verified payment.

## Current verified product position

- Product: HamidCognition Action Gate
- Published release: v1.1.1
- Release tag: `action-gate-v1.1.1`
- Published source: `e9ea7565f4ddea91f5c45104237bd20564c80894`
- Pilot: 30 days, one protected HTTP or MCP tool
- Proposed pilot fee: USD 7,500–10,000
- Delivery models: SELF_HOSTED / MANAGED / ENTERPRISE

The current mutable `main` branch is development state and must not be quoted as the customer artifact until a new release is deliberately cut and its evidence is complete.

## Sales sequence

### 1. Prepare the buyer package

Send only the narrow product story:

- one-pager;
- 12-minute demo;
- pilot scope;
- acceptance matrix;
- pricing/scope;
- release provenance.

Do not send the research portfolio as the primary sales story.

### 2. Find the right buyer

Prioritize teams already deploying agents with write access to:

- internal APIs;
- databases;
- cloud resources;
- privileged administration;
- MCP servers;
- high-impact business workflows.

The first contact should be a security/platform/AI-infrastructure owner, not a generic corporate inbox.

### 3. Sell the test

The initial message is not "buy an AI safety platform."

Use the concrete proposition:

> Give us one high-impact agent tool. We will put an authorization boundary in front of it and test whether unauthorized, expired, replayed or tampered execution is rejected at the protected-tool boundary.

### 4. Qualify before building

A prospect is qualified only when all are known:

- target tool;
- owner;
- deployment environment;
- authentication model;
- representative allowed and denied actions;
- acceptance authority;
- commercial buyer;
- feasible payment route.

If these are unknown, do not start custom engineering.

### 5. Close the pilot

The pilot agreement must contain:

- exact protected tool/path;
- deployment responsibility;
- duration;
- fee;
- acceptance tests;
- customer responsibilities;
- known limitations;
- support boundary;
- license/usage terms;
- payment terms;
- termination/rollback terms.

### 6. Execute acceptance

Run the agreed tests in the customer's environment.

Record:

- source/release identifier;
- configuration;
- test results;
- evidence artifacts;
- exceptions;
- customer acceptance.

### 7. Convert

After acceptance, present the next deployment mode based on actual customer needs. Do not sell Managed/Enterprise capabilities as operationally proven before they are actually delivered.

## Revenue evidence

The first revenue record needs:

- customer identity;
- agreement/invoice identifier;
- amount and currency;
- payment method;
- transaction hash or provider confirmation;
- settlement date;
- entitlement/delivery record;
- acceptance record.

A GitHub release, a website visit or an email sent is not revenue.

## Operating rule

Do not add product features merely because a prospect has not replied. The first bottleneck is customer contact and acceptance, not another architecture layer.

Do not modify GitHub Actions workflows to create sales evidence. Engineering evidence and commercial evidence are separate systems.

## First-customer scoreboard

Track only these states:

**PROSPECT → QUALIFIED → DEMO → PILOT PROPOSED → AGREEMENT → PAID → DEPLOYED → ACCEPTED → RENEWAL**

A state changes only when external evidence exists.

## Immediate external work

The remaining work that cannot be truthfully completed by repository code alone is:

1. identify real qualified buyers;
2. conduct the demo;
3. issue the pilot quote/agreement;
4. obtain payment through the configured settlement route;
5. deploy against the buyer's tool;
6. capture acceptance evidence.

Those are the steps that turn software into a business. Humanity did, eventually, invent invoices for this exact reason.
